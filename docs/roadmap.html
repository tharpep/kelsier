kelsier · kel

Five stages, each gated on the last

The constraint is “will I actually adopt this,” not “can it be built.” So every stage ships the smallest thing that answers a real question, and nothing above a line gets built until the stage below it has earned its place in daily use. If v0 doesn’t stick, none of the rest happens.

    Stage 0  v0 · premise test

    Prove the idea before building it

    Shell scripts and tmux config. No binary. This exists to test one thing.

    Ships
    • kel-status — a shell script that renders the status-left fleet line
    • kel-jump — prefix ` jumps to the next session in waiting
    • 3 Claude Code hooks write <state> <epoch> atomically; SessionStart stashes the window id
    • install.sh merges the hooks into settings.json with jq, without clobbering MCP servers
    • sessions are native tmux windows, made by hand
    Gate to start

    None — this is the entry point.

    Still manual

    Creating windows, adding worktrees, cd-ing into repos.

  2. 1

    Stage 1  v0.1 · session lifecycle

    Automate the parts of v0 you got tired of typing

    The first shell scripts become real subcommands.

    Gate — the pain that unlocks it

    You’re hand-rolling git worktree add + tmux new-window + cd several times a day.

    Ships
    • kel new <name> · kel new <name> --worktree · kel kill <name>
    • kel ls [--json]
    • kel kill refuses on uncommitted or unpushed worktree changes, and says why
    • kel doctor — capability probe, cached per machine

    UnlocksOne command spins up a named session in the right place; one command tears it down without eating uncommitted work.

  3. 2

    Stage 2  v0.2 · worktrees for real

    Make parallel work on one repo actually usable

    A fresh worktree with no dependencies installed is worthless. Fix that, and prove kel isn’t Claude-Code-only.

    Gate — the pain that unlocks it

    Worktree sessions are dead on arrival: no node_modules, no .venv, no .env, no build cache.

    Ships
    • .kel/setup — per-repo executable, runs in the new worktree with $KEL_REPO
    • a second agent adapter (a non–Claude-Code agent) to prove the adapter boundary is real
    • agents with no hook system fall back to unknown + the pane’s last output line

    Unlockskel new --worktree gives you a checkout you can work in immediately — and kel can track agents it has no hooks for.

  4. 3

    Stage 3  v0.3 · the board

    Give the fleet a real surface — only once the status line stops fitting

    A transient popup, not a pane. Opens over the current window, dismissed with a key.

    Gate — the pain that unlocks it

    Routinely more than ~6 sessions. The status line is truncating and you need filter / scroll / browse.

    Ships
    • kel board as a display-popup TUI (shell TUI, or Bubble Tea if it needs the structure)
    • filter, jump, new, kill — from the board
    • the board never occupies a pane and never needs to survive a switch

    UnlocksManaging 10+ sessions without the status line turning to mush.

  5. 4

    Stage 4  v1.0 · consolidation

    Turn the pile of scripts into one thing you install anywhere

    Go + Bubble Tea, single static binary. Only worth it once the scripts are load-bearing.

    Gate — the pain that unlocks it

    The shell scripts got slow or hairy — or you want it on a second machine cleanly — or it’s ready to show people.

    Ships
    • one static binary replacing kel-status / kel-jump / kel board
    • ~/.config/kel/config.toml + per-repo .kel/config.toml
    • a README that leads with the layout and the jump key; MIT license

    Unlocksgit clone && ./install.sh on any machine — and a public repo, if you decide you want one.

Cut — the two-slot / swap-pane architecture

One visible window split in two, every agent and editor living in a hidden holding session, swapped into the visible slots with swap-pane. Recorded here so the idea has a written answer and doesn’t get re-proposed.

Hidden holding session on top; two visible slots below. Every switch moves a pane.

Shipping instead

1 auth-fix2 rate-limit3 docs
kel board  (popup, on demand)

Native tmux windows. The board is a transient popup over whichever window you’re in.

  • swap-pane is the hardest thing in the design and gives less flexibility than native windows — no real side-by-side comparison.
  • the holding session’s pane geometry desyncs on every terminal resize; the next swap-in janks.
  • prefix 1–9 collides with native tmux window switching — a muscle-memory tax everywhere else, forever.
  • three panel modes fighting over one slot means you can’t see the board while editing.
  • the status line breaks past ~6 sessions anyway — which is exactly when the popup board earns its place.

Order is the contract. Each stage is gated on the one below it proving itself in daily use. If v0 doesn’t stick — if the status line becomes noise you ignore, or the hooks misfire enough that you stop trusting the state — nothing above it gets built, and that’s the point.
