kelsier · kel

Five stages, each gated on the last

The constraint is “will I actually adopt this,” not “can it be built.” So every stage ships the smallest thing that answers a real question, and nothing above a line gets built until the stage below it has earned its place in daily use.

Status · 2026-08-29: v0 through v0.4 are shipped and in use. Only v1.0 (the Go rewrite) remains, and it's optional — decided after living with the shell version. Authoritative build order and test plan live in docs/rollout.md; this page is the visual companion.

  2. ✓

    Stage 1  v0.1 · session lifecycleshipped

    Automate the parts of v0 you got tired of typing

    The loose scripts consolidate into one kel command.

    Shipped
    • kel new <name> [-w] — window + agent, inplace or in a git worktree; a worktree runs the repo’s .kel/setup (this was v0.2, folded in)
    • kel kill <name> — removes the worktree; refuses on uncommitted / unpushed work unless -f, and shows what’s at risk
    • kel ls [--json] · kel doctor (cached)
    • kel restore [-c] rebuilds windows after a kill / reboot; -c resumes each conversation by its recorded session id
    • kel prune discards dead session records; one tmux session kel, kel new works from any shell

    UnlockedOne command spins up a named session in the right place; one tears it down without eating uncommitted work; a kill or reboot is recoverable.

    Give the fleet structure — and the first select-and-see surface

    One tmux session per repo, plus kel menu: a dynamic list of every agent, press a key to jump. Commands stay primary.

    Shipped

    A transient display-popup running fzf — not a hand-rolled TUI. ~50 lines.

    Shipped

  5. ✓

    Stage 4  v0.4 · UX & learnabilityshipped

    Make it one navigator, safe to fumble, learnable without the docs

    A review (mine + Gemini via agy) — core loop solid, friction for a newcomer. No new features.

    Shipped
    • One navigator, then one job per key. A second review pass (Gemini 3.1 Pro) caught the board’s key legend truncating in the popup and its actions being invisible chords. Final shape: Ctrl+Space / prefix b = find an agent (compact footer; enter jumps, tab opens a labelled menu — jump / new here / rename / go to group / kill). prefix m = manage the agent you’re on. prefix k = the “new to kel?” primer. `` = jump to whoever’s waiting. The old quick-jump display-menu is retired.
    • Trust bugs fixed. kel rename (+ prefix ,) keeps the metadata record in sync; both menu “new agent” paths route through kel new; the board’s kill always confirms; a crashed agent reads as dead / x instead of stuck on working.
    • Learnability. first-run prints the three keys that matter; bash + zsh completion (agent names for kill, groups for go/move); Shift+drag copy tip surfaced in kel cheat.
    • Group model. non-repo kel new/move warn about the misc fallback; kel move warns on a worktree/group mismatch; monorepo split documented.

    UnlockedFour keys, four jobs: waiting / find / manage / learn. Fumbling one no longer desyncs state.

Cut — the two-slot / swap-pane architecture

One visible window split in two, every agent and editor living in a hidden holding session, swapped into the visible slots with swap-pane. Recorded here so the idea has a written answer and doesn’t get re-proposed.

Rejected

↓  swap-pane  ↓
left slotright slot

Hidden holding session on top; two visible slots below. Every switch moves a pane.

Shipping instead

1 auth-fix2 rate-limit3 docs
kel board  (popup, on demand)

Native tmux windows. The board is a transient popup over whichever window you’re in.

  • swap-pane is the hardest thing in the design and gives less flexibility than native windows — no real side-by-side comparison.
  • the holding session’s pane geometry desyncs on every terminal resize; the next swap-in janks.
  • prefix 1–9 collides with native tmux window switching — a muscle-memory tax everywhere else, forever.
  • three panel modes fighting over one slot means you can’t see the board while editing.
  • the status line breaks past ~6 windows anyway — which is what v0.2 grouping and then the v0.3 board are for.

Order is the contract. Each stage is gated on the one below it proving itself in daily use — if the status line becomes noise you ignore, or the hooks misfire enough that you stop trusting the state, nothing above it gets built, and that’s the point. v0 through v0.4 have each cleared that bar and are in daily use; v1.0 waits until the shell version actually strains.
